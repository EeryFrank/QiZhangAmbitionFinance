# 管理员使用说明

当前目标是本服 Minecraft 26.3、NeoForge 26.3.0.50-beta 与 Youer 环境。核心与可选生活服务模块已经拆分；**本次拆分版本的实际运行、交易及重启验证仍待完成**。数据检查、编译通过不能代替运行验收。其他版本、Vault 和热门商店插件的适配见 [路线图](ROADMAP.md)。

## 安装与已有存档

金融核心位于 `finance`，显示名为 QiZhangAmbitionFinance，保留 `cozylife_economy` 注册 ID、铜银金币 ID 和原有财务存档目录。`cozylife-integration` 提供可选的 QiZhangCozyServices 菜单、家园与玩家传送；它依赖核心。实体币和菜单需要客户端安装对应模组。不要把旧的合并经济 JAR 与拆分后的核心同时加载。

只安装核心不代表已经有 Bukkit/Vault 经济提供器。此版本没有正式的 VaultBridge，也没有宣称已与 LuckPerms 自动对接。构建方法见 [BUILDING.md](BUILDING.md)。

铜币、银币、金币分别等于 1、100、10,000 点余额。玩家右键使用一整叠普通实体币存入余额；改名或附带非默认数据的硬币不自动存入。商店兑换实体币需要足够背包空间。管理员发币走物品邮箱，**不会直接增加钱包余额**；玩家领取后再自行存币。

付费传送实行足额先扣：不足额不会调用传送，成功后核实位置与存档并提交；确定没有移动的失败会退回本次预扣。若玩家已移动但回调报错，或存储状态无法核实，系统保留收据待查，不能按“确定失败”再次人工补发退款。

## 管理命令

命令主入口是 `/qzeconomy`，别名 `/qzfinance`。服务器本机控制台输入时可不带 `/`。`#001` 是商品编号，不是物品 ID；按 `list` 当前结果选择编号。以下示例只有在主动执行时才生效。

| 命令尾部 | 用途 |
| --- | --- |
| `list`、`show #001` | 查看目录和单个商品 |
| `estimate minecraft:iron_sword` | 查看本服官方参考价、依据和限制 |
| `enable #001 true` / `false` | 上架或下架 |
| `category #001 building` | 调整分类：`building`、`ores`、`farming`、`equipment`、`modded`、`rare` |
| `price #001 20` / `price #001 auto` | 设置官方买价；`auto` 恢复价格库买价。该命令同时将该物品当前市价重置到新基价 |
| `sellprice #001 3` / `sellprice #001 auto` | 设置独立回收基准；设为 `0` 同时关闭回收 |
| `limit #001 128` | 每玩家、每日、每个真实物品的回收件数 |
| `recycle #001 true` / `false` | 单品回收开关 |
| `step 0.0001` | 每成交一件对共享市价的浮动比例，不是整批只动一次 |
| `activity global true 0.9` | 全场九折；`false 1` 关闭 |
| `activity #001 true 0.95` | 单品九五折；与全场活动相乘 |
| `profile small` / `medium` / `large` | 手动应用金融档位的建议成交步长 |
| `rule <调控项> <值>` | 修改下表中的业务规则 |
| `config export` / `validate` / `apply` | 文件编辑流程 |
| `permissions reload` | 校验重载管理权限，刷新在线玩家指令树 |

新增草稿的完整语法：

```text
/qzeconomy add minecraft:iron_sword auto equipment auto auto 铁剑
/qzeconomy add <物品ID> <整数买价或auto> <分类> <每日额度或auto> <回收基准或auto> <中文名称>
```

`add` 先下架保存；`addlive` 使用相同参数直接上架。两者都默认关闭新商品回收。当前商品目录最多 128 条，不能把 7,246 项参考库直接当作全部已上架目录。真实物品必须已注册；重复物品请管理原编号。同一真实物品的别名共用买价、市况、回收、每日额度及活动参数。中文名称不超过 40 字符。

买价是 1 至 1,000,000,000 的整数；回收基准可以为 0，否则必须低于买价。额度为 0 至 100,000。打开单品回收时仍需正的基准和正的额度；`rare` 分类禁止回收。低值基础块、矿锭、矿块、基础材料压缩块以及原木以外的木制建材禁售，人工填写价格也不能绕过。技术、创造或依赖特殊组件价值的条目禁止进入普通商品目录。

## 可调经济规则

`rules` 中缺省开关按开启处理，数值采用下表默认值。修改成功会原子保存并使旧报价失效。

| `rule` 调控项 | 默认 | 允许值与影响 |
| --- | --- | --- |
| `dynamic_pricing` | `true` | 关闭后成交不再逐件推动市价；不会把既有市价自动重置 |
| `recycle` | `true` | 全局回收总开关；关闭时所有商品暂停回收 |
| `daily_recycle_limit` | `true` | 是否检查日额度；关闭后仍记录实际回收数量，重开后不会重置已用量 |
| `weekly_reversion` | `true` | 是否按周将市价偏离幅度回调到基价 |
| `weekly_reversion_ratio` | `0.2` | 0–1。每周将与官方基价的差额收回该比例 |
| `vip_discounts` | `true` | 是否应用 VIP 购物折扣，不删除 VIP 有效期 |
| `min_market_multiplier` | `0.5` | 0.1–1，共享市价最低为官方买价乘此值 |
| `max_market_multiplier` | `1.5` | 1–5，共享市价最高为官方买价乘此值 |

例如 `rule min_market_multiplier 0.6`、`rule max_market_multiplier 1.4` 将价格范围改为 60%–140%。默认 50%–150% 是业务配置，不是不可修改的底层限制。

`step` 范围为 0–0.01，支持最多 12 位小数。小型档 1–19 位活跃玩家使用 `0.0001`，中型档 20–49 位使用 `0.00005`，大型档 50 位及以上使用 `0.00002`。推荐依据近 7 天活跃玩家人数，**只建议、不自动切换**。切档只更新档位标记和步长，不重置余额、官方价、市价、VIP 或已用额度。观察期、最大周调幅、最小样本是人工管理参考，不是已实现的自动控价任务。

日界与周一结算使用 `Asia/Shanghai`。已有市价只在配置许可的范围内浮动；批量买卖逐件结算并显示整批实际总额。独立回收基准随 `共享市价 / 官方买价` 缩放，向下取整、至少 1 点，上限为同一次实际买价减 1；实际购买价为 1 或基准为 0 时暂停回收。允许正常生产加工利润，不对所有配方差价一概拒绝。

不可关闭的安全约束包括：整点货币、不得负余额或数值溢出、实际买卖至少 1 点价差、一次性报价与存档收据、幂等请求检查、真实物品与组件核验、技术品和服主禁售限制。

## 文件编辑接口

运行中的真实商品配置保存在世界账本中。`config/cozylife-economy-market.json` 是初始化种子，不是随改随生效的在线配置；已有账本时不要靠改种子覆盖现有状态。

1. 执行 `/qzeconomy config export`。生成 `config/qizhang-finance/managed-market.json`；已有导出会保留带时间编号的旧副本。
2. 编辑其 `config` 对象。外层 `schema=1`、`expected_config_revision` 保持导出值；内部 `config.schema=3`。文件须不超过 1 MiB。
3. 执行 `/qzeconomy config validate`，只校验、尚未应用。
4. 执行 `/qzeconomy config apply`。如果期间其他管理员修改配置，旧导出会被拒绝，需要重新导出并合并改动。

这一路径只替换业务配置，保留余额、VIP 和已用回收额度。现有市价保留后按新的上下限夹取，新物品从基价初始化。它与 `price` 命令直接重置该物品市价的行为不同。

文件可编辑 `step`、`finance_profile`、`rules`、全场活动、`vip_normal_discount`、`vip_activity_discount`、交易冷却、`checkin` 与 `products`。折扣必须大于 0 且不超过 1；默认普通 VIP 折扣 `0.95`、活动期间额外乘数 `0.98`。VIP 价格 77,777 点、每次延长 7 天目前是代码常量，不是这个配置接口的可调字段。剩余时间大于 21 天时不能续期，恰好 21 天可续到 28 天；每次成功购买或续期同时获得 1 次永久补签机会。交易冷却范围 4–200 tick。

### 签到、永久补签与里程碑

签到按北京时间（`Asia/Shanghai`）自然日结算，不要求连续在线 24 小时。第 N 个连续签到日的默认余额奖励是 `floor(100 × 1.01^(N−1))`；领取时 VIP 有效则为 `floor(100 × 1.01^(N−1) × 1.05)`。小数参与后续复利，仅实际发放时向下取整，不会每天把小数抹掉。未签到的今天若昨天已签到，连续天数仍显示昨天结束时的连续天数。

每次 VIP 购买赠送的补签次数永久保留，不随 VIP 到期清除。注册后、今天之前的漏签日可消耗 1 次补签：奖励依据补入后截至该日的完整连续天数，VIP 加成依据领取时状态。补签连接其后的已签到日期时，这些日期会计入新的最长连续段；它们已经结算的金额不追差。未来、注册前或已领取的日期不能补签。

连续 7/14/30/60/100 天默认分别一次性奖励 1/3/10/20/50 枚银币，存入物品邮箱。每账户每个天数阈值仅领取一次；同次补签可解锁多档。余额、补签次数、日期记录、里程碑记录和银币邮件在同一账本事务内保存。邮箱满、奖励溢出或保存失败时，不会只扣补签次数。余额不能超过有符号 64 位整数上限；默认复利不另设每日奖励封顶，超出安全数值范围会中文拒绝，由管理员调整规则。

现有账户没有可靠首次加入时间时，以升级后首次真实登录的北京时间日期登记；账户存在、最后在线时间、文件修改时间和离线 API 入账均不用于猜测更早日期。已有可验证的 `first_join_at` 或 `first_seen`（毫秒时间戳）才允许作为迁移来源，并在账户记录来源。登记后不会因重启或配置变更重置。

通过前述 `config export → validate → apply` 流程调整 `config.checkin`，默认内容如下。不要直接修改生产账本中的已结算日期或次数。

```json
{
  "enabled": true,
  "base_reward": 100,
  "growth_factor": "1.01",
  "vip_multiplier": "1.05",
  "milestones": {"7": 1, "14": 3, "30": 10, "60": 20, "100": 50}
}
```

基础奖励是正整数，两种倍率至少为 1，支持最多 12 位小数；里程碑最多 32 档，值为 1–1,000,000 枚银币。关闭签到只阻止新的领取，不清空记录或永久补签次数；修改奖励不追溯重算历史，新配置会使尚未确认的签到报价失效。移除再加回同一天数的里程碑也不会重复发奖。界面确认报价有效 30 秒，跨北京时间零点、VIP 到期或账户变化后需重新选择日期。

官方参考库位于 `config/qizhang-prices/QiZhangOfficialPrices.json`，首次不存在时从核心资源复制。该库不由 `config apply` 重载；更新应在维护停服时进行，并保留旧库和对应配置。新增注册物品若不在快照内，运行时仅补为保守未审价条目，不代表已经完成配方估价或跨整合包兼容。

## 权限分配

首次使用会创建 `config/qizhang-finance/permissions.json`。`schema=1`，默认 `default_op_level=4`；每个 `operations.<操作>` 可以配置 `op_level`（0–4）、`allow_players` 和 `deny_players`（标准 UUID 数组）。0 表示所有普通玩家达到等级条件，不是关闭操作。

操作名包括 `list`、`show`、`enable`、`category`、`price`、`sellprice`、`step`、`recycle`、`limit`、`activity`、`add`、`addlive`、`estimate`、`profile`、`rule`、`grantcoins`、`export`、`players`、`stats`、`job`、`rewards`、`config`、`permissions`。外部解析器对应节点为 `qizhangfinance.admin.<操作>`；仅写这些节点到某个权限插件中，**不会自动建立集成**。

示意结构（空名单不包含任何真实玩家）：

```json
{
  "schema": 1,
  "default_op_level": 4,
  "operations": {
    "estimate": {"op_level": 2, "allow_players": [], "deny_players": []},
    "grantcoins": {"op_level": 4, "allow_players": [], "deny_players": []}
  }
}
```

真实本机服务器控制台可管理；RCON、命令方块和伪装玩家的命令源不获此管理入口权限。玩家判定顺序是：UUID 拒绝名单 → 已注册外部解析器的明确返回值 → UUID 允许名单 → OP 等级。解析器返回 `null` 表示继续本地规则；抛出异常则拒绝。配置读取失败时玩家管理关闭，本机控制台仍可修复文件并执行重载。

## 实物币邮件和管理 JSON

发放语法：

```text
/qzeconomy grantcoins <已加入本服的玩家名或UUID> <copper或silver或gold> <数量> <jobUUID>
```

每次 1–100,000 枚；目标必须是本世界已知、实际加入过的玩家。同一 `jobUUID` 重试必须保留收件人、币种、数量，成功重复请求只返回 `replay=true`，不再投递；改变参数会被拒绝。单币种邮件上限 1,000,000 枚，邮箱最多 256 条，管理员发放凭据最多 10,000 个，达到上限不会自动清除旧编号。任务编号要在执行前持久保存，结果不明时先核查原任务，不能换编号重发。

面板/脚本可经获授权的本机控制台发送 `qzeconomy api <requestUUID> <操作> ...`，日志使用 `QZECONOMY_JSON ` 前缀，返回 `schema`、`request_id`、`operation`、`ok`、`data`、`error`。请求编号用于关联本次回复，发币的 `jobUUID` 才是持久任务编号。

- 读取：`export`、`players`、`stats`；`estimate <物品ID>`；`job <jobUUID>`；`rewards <战利品表ID>`。
- 发币：`grantcoins <目标> <币种> <数量> <jobUUID>`。
- 管理：`command <白名单商品命令尾部>`，只接受商品及规则白名单，不是任意服务器命令执行器。`config` 和 `permissions` 不在该 `command` 白名单中。

`job` 返回 `found` 和 `receipt`；发币成功回执含 `delivery="mailbox"`、`balance_changed=false`。玩家列表为空时等待真实玩家加入，不创建假账户填充列表。返回 `STORAGE_UNAVAILABLE` 或写入结果不明时，保留原任务编号、日志与文件，修复后核查/重试原任务。

## 账本备份、恢复和人工估价

正式账本是 `<世界目录>/cozylife-economy-v2/state.json`，审计记录为同目录 `transactions.jsonl`，独占文件锁为 `state.lock`。状态中包含账户、市价、VIP、额度、邮件、管理员任务和开发 API 幂等凭据。玩家 `playerdata` 中还保存交易收据，实体币也可能在玩家背包和世界容器中。

可靠备份流程是正常停服，确认进程退出，再保留同一时间点的完整世界、上述账本、配置与物价库。恢复时同批恢复世界/玩家数据/账本，不能只回滚 `state.json` 或只恢复某个玩家背包；保留现状副本用于核对。`transactions.jsonl` 是审计记录，不是可以独立重放还原所有物品的完整备份。

启动时会用已保存玩家收据核实未完成交易；无法判定时保护停用，不自动清零。不要删除 `pending`、收据、任务号或锁文件来强行解锁，也不要在运行时手改余额。先核对磁盘、文件权限、配套存档与日志，再选择同批恢复。恢复方案仍需在隔离副本实测后用于正式服。

本服参考库覆盖 7,246 项，但仅 51 项沿用已有人工设置买价。其余根据配方、自然来源与明确假设生成，并带可信度；838 项低可信不得 `auto` 核价，技术/禁售项无论手填或自动都不允许普通上架。详细算法、量产/概率边界和发布数据见 [本服定价配置](../pricing-profile-cozylife/README.md)。
